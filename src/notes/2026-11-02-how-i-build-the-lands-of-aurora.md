---
title: How I build The Lands of Aurora
summary: A fairy-tale soulslike with coop, built in twenty days by one backend engineer and AI coding agents. The interesting part isn't the AI. It's the engineering discipline that keeps it on track.
---

*The Lands of Aurora* is a cartoon, fairy-tale soulslike: a third-person open world with bosses you learn, Rest Fires, coins you drop when you die, and coop for up to four players. It's meant to feel like Elden Ring's structure with Wind Waker's mood, and to be a lot less punishing than either.

I'm a backend engineer, not a game developer. I build it with AI coding agents doing most of the typing, while I act as director, designer, playtester and the person who makes the art. Twenty days after the first commit, the project looks like this:

| What | How much |
|---|---|
| Commits | 539, from 11 to 30 October 2026 |
| Code | 686 GDScript files, about 224,000 lines |
| Design documents | 146, written before the code they describe |
| 3D models | 1,132, generated by scripts or rebuilt from AI images |
| World | a 2 × 2 km continent with 8 biomes, plus an underworld |
| Bosses | 20 on the surface, each with 2–3 phases |
| Automated checks | a 63-test suite that runs headless on a clean copy of the code |

Those numbers only mean something because of how the work is organised. AI agents write code fast and confidently, including when it's wrong. Most of what I do is build the structure that catches it, which turns out to be the same thing I do in backend teams.

## Design documents come before code

Every system has a Markdown design document before it has code: the camera, combat, coop, the map, each boss's moves, each dungeon. They follow the same shape: a version and a date, pointers to the data file, the code and the test that prove it, and open questions marked as decisions for me. Some commits are literally "design only, no code".

Dungeons go one step further: their floor plans are generated by small Python scripts that also check the layout, for example the walking distance from the last Rest Fire to the boss. A concept image, a plan and a cross-section exist before a single wall is placed.

One file keeps it honest: a production ledger listing every feature as done (with the commit or test that proves it), to do, or waiting for my decision. Balancing numbers never live in code. There are 160 JSON data files, and the design documents keep repeating the same rule: "all the numbers are in the data file."

## Two ways to make 3D models

**Generated by code.** For the first two weeks almost every model came from Blender Python scripts run headless: 181 scripts, about 57,000 lines, producing rounded low-poly shapes with flat colours, with each moving part as a separate object pivoted on its joint so the game can animate it. A new boss is one game script plus one Blender script.

**Rebuilt from images.** From 24 October I added a second path for the things that needed more character. The agent writes English image prompts; I generate the concept images, keep the best of four, and turn them into 3D models in Tripo by hand. Then agent-written Blender tools take over: they recognise each model by its shape, rescale it to its category, reduce it and pack its textures into a shared atlas. That's how 195 of the 204 weapons, the trees, the village houses and the hero were rebuilt in three days.

The fiddly part is modular pieces. Walls and floors made by an image-to-3D tool don't meet cleanly, so the fitting tool measures, with raycasts in Blender, how far each mesh recedes at its edges and widens the piece by that much plus 1.5 cm. The 76-piece cave kit now reports zero gaps on 2,416 joints.

Taste stays a human job. On 24 October the first boss was swapped for an image-based model; I didn't like it, and it was reverted the same day.

## Animation: from springs to a real skeleton

At first there were no skeletons at all. Models were rigid parts animated by code, with damped springs adding squash, stretch and follow-through. Because the motion is computed only from state the network already shares, every player in coop sees the same thing without sending anything extra.

On 29 October the hero got a real 30-bone skeleton. A Blender script cuts the model, adds extra geometry at elbows and knees so they bend smoothly, and computes the skin weights (zero unweighted vertices out of 5,362). The motion clips come from Kimodo, a text-to-motion model running locally on my graphics card in about nine seconds per clip, from prompts like "a person walks forward at a steady relaxed pace, arms swinging naturally". A retargeting step maps them onto the game's proportions and finds the cleanest loop.

## Proving it works without opening the game

This is where the backend habits show most.

- **Every feature has a switch.** About 77 `--feature=off` flags let any change be compared with what was there before, or turned off without reverting code.
- **Every feature has a headless check.** There are about 122 test modes that run without a window and print a clear verdict line.
- **One command runs everything.** A script copies the latest commit into a clean folder, so unfinished work can't make a test pass by accident, runs 63 tests headless and exits with an error if any of them fails. It's CI, on my desk.
- **A bot fights every boss.** Each boss exposes where it can be hit. A test walks an invulnerable player from the region to the boss, through the fog wall and every phase until the boss dies and the rewards drop. The same test runs in coop with two game instances.
- **Screenshots from fixed cameras.** Because the world is generated from a fixed seed, a camera placed at a fixed point takes the same picture every time. Visual changes are reviewed as before-and-after pairs; the repository holds 924 screenshots, many of them in such pairs.

## The feedback loop: play, quote, fix

My main job is to play. When something feels wrong I write it down the way I'd say it, in Italian and without any technical framing, and the fix goes into a commit that quotes me word for word. 66 commits carry a dated quote. A few, translated:

- *"Distant trees are invisible and then they pop in."* The fix was flat impostors for far trees, three levels of detail with a dithered fade, and view distances up to 1.6 km.
- *"I need to understand which weapon it is already from the icon."* Every weapon got its own icon, rendered from its 3D model in the game's style.
- *"In a room where there's a bonfire, I take damage but I don't see enemies."* Dungeon enemies could hit through floors. Now they can't.
- *"The traps are too visible, I'd hide them a bit."* Traps are now hidden in the floor.

It works like a good product owner relationship. I describe the problem from the player's side; the fix and the reasoning end up in the history, where I can find them later.

## Three problems a backend engineer would recognise

**A world that never needs to be synchronised.** The continent is 2 × 2 km and must be identical for up to four players, without streaming terrain over the network or freezing the game. It's generated from a fixed seed, with a sub-seed per layer, on a background thread that starts while you're still in the menu, then attached a few chunks per frame. Every small variation, like the tint of a single rock, is a hash of its world position. The result takes about three seconds and is the same on every machine, so there's nothing to sync.

**Coop netcode and bugs that only show under stress.** The host is the authority: boss logic runs only there, and everyone else derives what they see from replicated state. Single player is the same code with one offline host. Three bugs taught me the most:

- A guest sometimes appeared with the default look, because the update with their appearance could arrive late. Appearance is now sent as a reliable, repeatable message.
- Coop dropped during long loading frames. A blocked main thread doesn't acknowledge network packets, and the default timeout is only a few seconds. I reproduced it with an artificial ten-second stall, then raised the timeouts.
- A sync test failed randomly. The causes were stale snapshot files and enemies that kept moving. Snapshots are now written atomically and compared within tolerance boxes, and the test also runs through a proxy that adds latency and packet loss.

**Performance from measurements, not guesses.** In the underworld the frame took 16.1 ms while the GPU worked for 2.5 of them: the CPU was the problem. Around 400 far-away enemies were animated every frame and traps ticked in rooms nobody was in. Putting distant enemies to sleep, with some hysteresis so they don't flicker between states, brought the frame to 6.4 ms. A 1.8-second freeze after respawning turned out to be the physics engine rebuilding one huge collision body; splitting it and spreading the work across frames brought it to 0.46 s.

## What I've learned so far

- **The agent writes the code; the structure decides whether it's right.** Design documents, data files, feature switches, headless tests and a clean-copy test run are what make speed safe. Without them, twenty days of fast commits would be twenty days of growing uncertainty.
- **Verification has to be cheap, or it won't happen.** One command for the suite, fixed cameras for screenshots, a bot for the bosses. If checking takes longer than building, nobody checks.
- **Humans keep the final word on taste and on what "done" means.** Reverting a model I didn't like took one sentence.
